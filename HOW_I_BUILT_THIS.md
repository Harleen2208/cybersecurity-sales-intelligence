# How I Built This

## Dev loop and agentic tools used

- **Claude** (chat) — primary pairing tool for architecture decisions,
  debugging the data pipeline (identifying the zstd compression
  format, writing/iterating DuckDB queries, diagnosing the entity-
  resolution bug), and iterating on prompt versions (v1 → v2).
- **Gemini (via API)** — not a dev tool, but the production LLM used
  inside the app itself, generating the rep-facing reasoning_summary
  text. Free-tier rate limits meant this had to be run in batches of
  ~30 companies at a time rather than as a single pass; 157 companies
  now have LLM-generated reasoning as a result.

No Loom walkthrough is included — it's listed as optional in the
brief, and given the compressed timeline I prioritised finishing the
required deliverables (hosted app, evals, docs) over an additional
video artifact.

## Where AI saved the most time

Diagnosing the dataset itself was the single biggest time save —
going from "this file won't open and shows garbage characters" to
correctly identifying it as zstd-compressed newline-delimited JSON
(Shodan-style internet scan data) happened in a handful of exchanges
rather than hours of manual trial and error. Scaffolding the repo
structure, SKILL.md, and eval harness shape also went much faster with
AI assistance than writing each from a blank page.

## Where AI cost more time than it saved

My first approach to filtering non-company domains (hosting providers,
CDNs) out of the scored results was a manual keyword blocklist —
excluding org names one at a time as new false positives kept
appearing. This required several rounds of patching because a
name-based blocklist can't generalise to a provider it hasn't seen
before. The actual fix — filtering by distinct IP-count per domain, a
structural signal rather than a name pattern — was available the
whole time, and I should have reached for it sooner instead of
continuing to patch a fundamentally limited approach.

## Known weaknesses I'd flag to a teammate

1. **Inconsistent tracing coverage.** 157 companies have
   LLM-generated reasoning_summary text, but only 21 of those calls
   went through the actual API integration (llm_reasoning.py) and are
   captured in traces.jsonl with full request/response/token/latency/
   cost data. The remaining 136 were generated by manually running the
   same prompt through Gemini's chat interface in batches, due to
   hitting the API free-tier rate limit — these have no structured
   trace data, since they never went through the logged code path.
   This is a real gap against the tracing requirement: in a production
   system, every LLM call must go through the traced API integration,
   not a manual workaround, precisely so this kind of blind spot can't
   happen. I'm flagging it explicitly rather than backfilling
   synthetic trace entries for calls that didn't actually happen
   through the code.
2. **Partial LLM coverage relative to the full hot tier**, independent
   of the tracing gap above — 157 companies is a subset of the scored
   base, not the complete hot tier.
3. **Scoring breadth gap.** The eval (30 hand-labelled examples, 86.7%
   agreement) surfaced that the rule-based scorer under-weights the
   *breadth* of moderate signals relative to a small number of severe
   ones — a company with several mild issues stacked together can
   score lower than a human reviewer's intuition would suggest.
