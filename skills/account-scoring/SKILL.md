# SKILL: account-scoring

**Version:** v2.0.0
**Status:** production (partial LLM coverage — see Known limitations)

## Purpose

Given company-level internet-exposure signals derived from Shodan-style
scan data, produce (1) a deterministic 0-100 prioritisation score and
hot/warm/cold tier via rules, and (2) a rep-readable natural-language
explanation via LLM. This is the core primitive the prospecting
dashboard ranks accounts by.

## Trigger conditions

- After the DuckDB aggregation pipeline produces/updates
  `companies.parquet` (one row per resolved company domain).
- After `scoring.py` produces `companies_scored.parquet`.
- On-demand, if a rep requests a fresh explanation for a specific
  account.

The LLM should never be called to compute or change the score itself —
only to generate the explanation text for an already-scored account.

## Inputs

| Field | Type | Meaning |
|---|---|---|
| eol_product_count | int | End-of-life software services exposed |
| eol_os_count | int | End-of-life operating systems exposed |
| self_signed_count | int | Self-signed certificates found |
| doublepulsar_count | int | DoublePulsar backdoor detected — near-certain existing compromise |
| malware_count | int | Active malware detected on exposed host |
| open_dir_count | int | Open directory listings exposed |
| exposed_database_count | int | Database services directly reachable from the internet |
| distinct_open_ports | int | Number of distinct open ports on the domain |
| rule_score | int | Pre-computed 0-100 score, passed in — never recomputed by the LLM |

## Outputs

```json
{"reasoning_summary": "A DoublePulsar detection indicates likely compromise, reinforced by EOL software, an EOL operating system, and a self-signed certificate, making this a critical Hot prospect."}
```

## Dependent prompts

Calls `prompts/account_scoring_v2.md` (production). `v1` is retained
in `prompts/account_scoring_v1.md` for eval comparison only — see that
file's changelog for what changed and why.

## Rule vs LLM split

**Rules (scoring.py, no LLM):** entity resolution (distinct-IP-count
thresholding per domain, exclusion of Shodan's `cloud`/`cdn`/
`honeypot` tags), all signal aggregation, the 0-100 score, and
hot/warm/cold tier bucketing. Deterministic, auditable, free, and
needs to run over a large row count cheaply.

**LLM (llm_reasoning.py):** only the natural-language
`reasoning_summary`. This is a genuine language-generation task —
synthesising several already-computed signals into one specific,
readable sentence — not something a fixed template or rule can do as
well.

## Model / cost

Development used Gemini's free API tier (model: gemini-3.6-flash, or
gemini-2.5-flash as fallback — see prompts/account_scoring_v2.md for
the model note). Free-tier rate limits meant only 21 of the
reasoning_summary generations went through the traced API integration
(logged in `traces.jsonl` with full token/latency/cost data); the
remainder were generated by manually running the same v2 prompt via
Gemini's chat interface in batches, as a timeline-constrained
workaround — these are not traced. See docs/architecture.md's cost
model section for full reasoning and the production recommendation
(all calls should go through the traced API path, not a manual
workaround).

## Worked example invocation

**Input:**
```json
{
  "eol_product_count": 1,
  "eol_os_count": 1,
  "self_signed_count": 1,
  "doublepulsar_count": 1,
  "malware_count": 0,
  "open_dir_count": 0,
  "exposed_database_count": 0,
  "distinct_open_ports": 4,
  "rule_score": 100
}
```

**Output:**
```json
{"reasoning_summary": "A DoublePulsar detection indicates likely compromise, reinforced by EOL software, an EOL operating system, and a self-signed certificate, making this a critical Hot prospect."}
```

(This is a real example from the shipped app — company `vodafone-ip.de`.)

## Known limitations

- Entity resolution is heuristic (IP-count threshold + tag exclusion),
  not ground-truth — some ISP/telecom domains (e.g. vodafone-ip.de)
  pass through despite representing shared carrier infrastructure
  rather than a single business. A production system would resolve
  entities against a verified business registry.
- Only 21 of 157 reasoning generations are traced with full
  observability data; the rest bypassed the logged code path due to a
  free-tier rate-limit workaround.
- Scoring weights are reasoned from security-domain knowledge, not
  validated against real sales-outcome data.
